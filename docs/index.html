An experiment in ergonomics

Structural matching that feels like String

includes, indexOf, replace, replaceAll — the methods you already know, asking questions of syntax instead of characters. For any language, over parsers that already exist, without a printer touching a byte you did not ask it to.

Start the tutorial → API reference Source

⚠️ Experimental, and not actively maintained

This started as a question — what if structural matching felt like String.prototype? It went further than expected: 13 packages, 950+ tests, and a real migration of a large Vue / Twig codebase. But it is a spike, not a product. There is no release cadence, no support, and no promise the API stays still.

If you want to take it over, please do. Fork it, rename it, publish it. Open an issue and I will happily hand over the repository or point people at yours. 🙂

Why not a regex

A text matcher has no idea what a balanced call expression is. Ask it for the argument of foo(…) and it has to guess where the argument ends:

A lazy regex

/foo\(([^)]*)\)/.exec("foo(bar(1, 2))")[1]

// "bar(1, 2"   ← stopped at the first )

codestring

js.parse("foo(bar(1, 2))")
  .match(code`foo(${arg})`)!.get(arg).text()

// "bar(1, 2)"  ← one CallExpression, offsets 4–13

The hole sits in a grammar position, so the parser decides where the capture ends. The same is true of every question: includes(code`console.log(${any()})`) is false for a "console.log(" that happens to sit inside a string literal, and true for one written across three lines.

A taste of the whole thing

import { any, capture, code, createLanguage } from "@codestring/core";
import { javascriptAdapter } from "@codestring/javascript";

const js = createLanguage(javascriptAdapter);
const arg = capture("arg");

js.parse(source)
  .replaceAll(code`console.log(${arg})`, code`logger.debug(${arg})`)
  .replaceAll(code`legacyFetch(${url})`, code`fetchJson(${url})`)
  .removeAll(code`debugger;`)
  .text();

Rewrites answer with a new document, so they chain and never mutate. And the output:

- console.log(  'a',    b  );
+ logger.debug('a',    b);

The arguments come through exactly as written — quote style, the spacing between them, a comment in the middle — because the rewrite inserts the source they were written with rather than printing them again. There is no printer anywhere in this library. Every byte outside an edit range is the byte that was there before.

Four pieces

The document

Parse once, then ask a String-shaped question. Nodes answer the same questions, scoped to their own subtree.

Codemods

A rule is a language, a glob, and one function. verify refuses a rewrite that broke the file before it reaches disk.

ESLint rules

Find this shape, say that, fix it like this — over the AST ESLint already built, whatever parser it was configured with.

Adapters

Five functions wrap a parser you already have. No matching logic, ever. A contract suite proves it behaves.

The core knows no grammar

Everything above works for Twig because someone wrote thirty lines that tell the core how to read a Twig node's kind, range and children. Everything the library does — captures, repetition, matching, edits, cross-language composition — lives in one language-agnostic core, and an adapter implements no matching at all.

AdapterBacked byReads

Nesting composes. A .vue file is HTML with JavaScript in one element and CSS in another, and inside() re-reads a captured region with another language, rewrites it there and splices the result back — in one pass, so several embedded regions can be rewritten without their offsets drifting.

Install

The core has no parser dependencies and never will, so you only install the parsers you use:

pnpm add @codestring/core @codestring/twig     # Twig only — no parse5, no acorn

Or take everything in one install:

pnpm add codestring
import { createLanguage, capture, code, twigAdapter } from "codestring";
import { vueAdapter } from "codestring/vue";  // subpaths stay tree-shakeable

What it is not

No universal AST, no type or symbol analysis, no formatting or AST printing, no import management, no cross-file refactoring, no query language separate from JavaScript.

Scope resolution is the big one. Answering “would a bare name emitted here resolve to a local binding?” needs a symbol table, and building one per language is a second product. Reach for your parser's own tooling there — @codestring/babel exists partly so a codemod can hold one tree and use @babel/traverse for scope while matching structurally over the same nodes.
