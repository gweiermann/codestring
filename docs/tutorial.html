Tutorial

From a first match to a codemod that rewrites markup, script and style in one pass — and then an ESLint rule written the same way. Every snippet below runs as written.

Experimental. codestring is an unmaintained experiment. Everything here works and is covered by tests, but there is no support and the API may move. Taking it over is very welcome.

Setup

pnpm add @codestring/core @codestring/javascript

Two imports and you have a language. createLanguage binds an adapter — the thirty-odd lines that tell the core how to read a parser's nodes — to the parse entry point and the pattern tag. 

import { any, capture, code, createLanguage } from "@codestring/core";
import { javascriptAdapter } from "@codestring/javascript";

const js = createLanguage(javascriptAdapter);

1 · The document is a String that reads syntax

language.parse() gives you the object you actually work with:

const file = js.parse(`
function load() {
  console.log("loading", id);
  return fetch(url);
}
`);

file.includes(code`console.log(${any()})`);  // true
file.count(code`return ${any()};`);          // 1
file.indexOf(code`fetch(${any()})`);         // a source offset, or -1

any() is a hole that binds anything and captures nothing. These are the questions a string answers — except includes is false for a "console.log(" written inside a string literal, and true for one spread across three lines.

Captures

A capture is a named handle you declare once and reuse. Interpolated into a pattern it is a hole; asked of a match it hands back what that hole bound: 

const arg = capture("arg");

const match = js.parse("foo(bar(1, 2))").match(code`foo(${arg})`)!;

match.get(arg).text();   // "bar(1, 2)"
match.get(arg).start;    // 4  — an offset in the original file
match.get(arg).nodes[0].kind;  // "CallExpression"

Handles hold no state, so the same handle can be used by several patterns and matched concurrently — the results live on the Match.

A node answers the same questions

The String-shaped surface is on every node too, so you can scope a question to one subtree: 

const fn = file.nodes().find((node) => node.kind === "FunctionDeclaration")!;

fn.includes(code`fetch(${any()})`);   // is there a fetch in *this* function?
fn.matchAll(code`await ${any()}`);
fn.count(code`return ${any()};`);

Why not just node.text()? Because handing that text to a pattern re-parses it on its own, where it can mean something else. { methods: {} } is an object literal inside a file and a block statement standing alone — the search would run over a tree that was never there and answer no. Searching a node searches the tree it already belongs to, and parses nothing.

2 · Rewriting

Every rewrite answers with a new document, so they chain and never mutate the one you had: 

js.parse(source)
  .replaceAll(code`console.log(${arg})`, code`logger.debug(${arg})`)
  .removeAll(code`debugger;`)
  .text();
  function load() {
-   console.log("loading", id);
+   logger.debug("loading", id);
    return fetch(url);
  }

In the second argument the same code fragment means the opposite thing: its holes are no longer slots but the source the match captured. "loading", id comes through with its own quotes and its own spacing, because it is inserted as source rather than printed from an AST.

Deciding per match

The replacement can be a function. Returning nothing leaves that match alone:

file.replaceAll(code`console.log(${arg})`, (match) =>
  match.get(arg).isEmpty() ? null : match.replace`logger.debug(${arg})`);

Inside a match the edit constructors are tagged templates that already know what was captured, so there is no second .get() and no separate source tag: 

match.replace`logger.debug(${arg})`                  // the whole match
match.replace(body)`<sw-block>${body}</sw-block>`    // one capture of it
match.insertBefore`// generated\n`
match.remove()                                       // or match.remove(handle)

They return plain edit objects, so a conditional rewrite is an if and a push: 

const edits = [wrapWithBlock(body, name)];
if (legacyAttribute) edits.push(remove(legacyAttribute));
return match.transform(edits);

3 · A real rewrite, in another language

Nothing so far was JavaScript-specific. Swap the adapter and the same vocabulary reads Twig: 

import { twigAdapter } from "@codestring/twig";

const twig = createLanguage(twigAdapter);
const name = capture("name");
const body = capture("body");

twig.parse(source).replaceAll(
  code`{% block ${name} %}${body}{% endblock %}`,
  code`<sw-block name="${name}">${body}</sw-block>`,
).text();

In

{% block header %}<h1>Title</h1>{% endblock %}
{% block main %}<p>Body</p>{% endblock %}

Out

<sw-block name="header"><h1>Title</h1></sw-block>
<sw-block name="main"><p>Body</p></sw-block>

The nesting is handled for you: a {% block %} around another {% block %} produces two matches whose edits do not collide, and both are applied in one pass.

4 · Codemods: rules, not scripts

A rule is a language, the files it applies to, and one function from parsed source to rewritten source. There is no from/to/where vocabulary to learn — the function decides everything, and returns nothing to leave the file alone. 

import { createTransformer } from "@codestring/codemod";

export const renameLogger = createTransformer({
  name: "console.log → logger.debug",
  language: js,
  fileGlob: "**/*.js",
  transform: ({ file, source }) =>
    source.replaceAll(code`console.log(${arg})`, code`logger.debug(${arg})`),
});

renameLogger.transformString("console.log(  'a', b  );");  // "logger.debug('a', b);"
await renameLogger.transformFiles(["src/"], { write: true });

Everything an option bag would do, the function does:

// skip a whole file
transform: ({ source }) => (source.includes(code`@generated`) ? null : rewrite(source)),

// gate by path
transform: ({ file, source }) => (file?.startsWith("src/") ? rewrite(source) : null),

// as many rewrites as you like, each reading the last
transform: ({ source }) => source.replaceAll(a, b).removeAll(c),

verify — refuse your own output

The one check a transform cannot express cheaply: re-read the finished file and reject a rewrite that broke it. It runs once per changed file and is on by default when writing to disk. 

verify: "parses",
verify: ({ before, after, path }) => after.includes("logger") || "logger is not imported here",
verify: false,   // opt out

A refusal throws TransformVerificationError carrying path and reason, so a runner reports which file was refused and why instead of writing something broken.

Several rules, one sweep

import { createCodemod } from "@codestring/codemod";

const migrate = createCodemod({
  name: "v2 migration",
  transformers: [renameLogger, renameMarkup, migrateVueTemplates],
});

const results = await migrate.transformFiles(["src/"], { write: true });

A codemod carries no language of its own. Each transformer brings one, so a single sweep reads .js with the JavaScript adapter, .html with parse5 and .vue with @vue/compiler-dom, and every file is read by whatever knows how to read it. Transformers run in order, each reading what the one before produced.

Each result reports { path, changed, before, after, written, applied }, where applied names the transformers whose glob matched and which actually changed something — so a dry run (write: false) tells you exactly what a real run would touch.

5 · Languages inside languages

A .vue file is HTML with JavaScript in one element and CSS in another. inside() re-reads a captured region with another language, rewrites it there and splices the result back — in one pass, so several embedded regions can be rewritten without their offsets drifting: 

createTransformer({
  name: "vue: markup, script and style",
  language: html,
  fileGlob: "**/*.vue",
  transform: ({ source }) =>
    source
      .replaceAll(code`<b>${x}</b>`, code`<strong>${x}</strong>`)
      .inside((block) => code`<script>${block}</script>`, js, (script) =>
        script.replaceAll(code`console.log(${arg})`, code`logger.debug(${arg})`))
      .inside((block) => code`<style>${block}</style>`, css, (style) =>
        style.replaceAll(code`color: red`, code`color: var(--danger)`)),
});

The first argument is handed the capture that stands for the region, so the pattern and the handle can never disagree about which hole holds it. Nesting depth is unbounded, and a nested match's edits still target the root document — the offsets never leave the original file. 

const body = twig.parse(file).match(block)!.get(blockBody);  // offsets 19..48 in the Twig file
const inner = html.parse(body);                             // parsed as HTML, offsets unchanged

inner.text();            // just the body
inner.document.text;     // the whole Twig file

6 · ESLint rules as patterns

An ESLint rule is usually a visitor, some node.parent walking and fixer arithmetic. Most of them are really “this shape is wrong, that shape is right”: 

import { capture, code } from "@codestring/core";
import { createRule } from "@codestring/eslint";

const args = capture("args");

export const noConsoleLog = createRule({
  meta: { type: "suggestion", fixable: "code", messages: { useLogger: "Use logger.debug instead." } },
  find: code`console.log(${args})`,
  messageId: "useLogger",
  fix: (match) => match.replace`logger.debug(${args})`,
});

It runs on the AST ESLint already built, so nothing is parsed twice, and because the tree is read structurally rather than by node type, whatever parser ESLint was configured with comes along — @typescript-eslint/parser included.

Narrowing, pointing, suggesting

createRule({
  find: code`t(${key})`,
  where: (match) => match.get(key).text().startsWith("'legacy."),  // narrow past the pattern
  report: (match) => match.get(key),                               // squiggle just the key
  message: "Legacy translation key.",
  suggest: "Drop the legacy prefix",                               // offer, do not apply
  fix: (match) => match.replace(key)`'${stripped(match)}'`,
});
OptionWhat it does
findThe pattern. The only required option.
whereNarrow further than a pattern can say — by what a capture bound, by its position, by anything.
message / messageId / dataThe report text, or a meta.messages key plus its placeholders.
reportPoint at one capture instead of the whole match.
fixReturn an edit, a list of edits, or replacement text. Returning nothing reports without offering a fix.
suggestOffer the fix as a suggestion rather than applying it automatically.
languageRead the file as something else — a Vue or Twig template rather than the script.
metaESLint's own meta, passed through untouched.

Fixes go through the same validation a codemod does, so a rule cannot emit two fixes that overlap, and match.remove() takes the statement's separator with it rather than stranding a comma. For anything needing scope, types or control flow, write the visitor — eslintLanguage(sourceCode) is exported so a hand-written rule can still ask structural questions of the tree ESLint gave it.

7 · The command line

Useful before you write anything: find out whether a pattern matches what you think it does.

cs find    -l twig       -p '{% block $name %}$$$body{% endblock %}' templates/
cs find    -l javascript -p 'console.log($$$args)' src/ --json
cs replace -l javascript -p 'foo($x)' -r 'bar($x)' --write src/
cs debug   -l javascript -p 'foo($x)'
cs languages

$name is one node, $$$name is a run of siblings, $_ and $$$_ are the same without capturing. With no paths, cs reads stdin. --adapter ./my-adapter.js loads an adapter you wrote yourself.

8 · When a pattern does not match

explain() says where the matcher got stuck, and what it wanted there instead:

js.parse("bar(1)").explain(code`foo(${arg})`);
no match; the closest attempt stopped at 1:1
  reason:   text
  expected: foo

debug() on a compiled pattern prints the intermediate representation, which is the fastest way to see whether a hole came out as one node or a run of siblings.
